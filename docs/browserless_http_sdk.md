# Browserless ChatGPT HTTP SDK — experimental boundary

This is the **opt-in direct HTTP** client introduced in PR #212.
It is **not** the older `assemble_product_runtime(transport="browserless-request")`,
and it does not start Chrome, a browser tab or the Native Messaging host.
The implementation uses the existing CWA authenticated session, curl and
Node.js 24+; it relies on a changeable private ChatGPT web protocol.

## Python API

Use one consistent installed package or source checkout; do not mix
an editable install from another CWA branch with selected files copied here.

```python
from pathlib import Path
from chatgpt_web_adapter.browserless_http import BrowserlessHTTPClient

client = BrowserlessHTTPClient(auth_file=Path("auth_data.json"))

first = client.send(
    "Explain the design briefly.",
    model="gpt-6-instant",
    on_token=lambda token: print(token, end="", flush=True),
)
print()
print(first.conversation.conversation_id)

next_turn = client.send(
    "Now point out one limitation.",
    conversation=first.conversation.conversation_id,
)
print(next_turn.text)

# New, separate ephemeral conversation:
temporary = client.send("Hello.", temporary=True)

# Optional, explicitly selected local attachments:
response = client.send("Summarize these notes.", media=[Path("notes.md")])
```

`prepare_next_turn()` is optional one-use preparation. It is not a
background scheduler, and an expired preparation is regenerated by the
library. Inspect `client.last_timing` after a send to understand latency.

## Deep Research direct HTTP launch (experimental, opt-in)

A genuine UI-launched Deep Research user message was observed carrying
`system_hints = ["plugin:connector_openai_deep_research"]`.
Direct HTTP can now **request** that product hint via the existing
two-phase conversation prepare/write flow:

```python
from chatgpt_web_adapter.browserless_http import BrowserlessHTTPClient

client = BrowserlessHTTPClient(auth_file="auth_data.json")
response = client.send(
    "Research an engineering question using credible sources.",
    model="gpt-6",
    reasoning_effort="high",
    deep_research=True,
)
research = client.get_deep_research(response.conversation.conversation_id)
print(research.status, research.report_id)
```

A user-run Windows live test on 2026-10-24 **confirmed** that one Direct
HTTP send with the explicit hint created a genuine Deep Research tool call.
Canonical readback observed the product widget in `researching` state
(`get_deep_research().status == "running"`), followed by `completed` with a
finished 53,965-character report and report ID. The report was fetched in a
separate process using canonical GET, with **no second Send**.

**Prompt integrity is a separate concern:** the test's Cyrillic source was
piped from Windows PowerShell to Python while PowerShell's pipeline output
encoding replaced Cyrillic characters with literal `?`. The persisted user
message and the tool's `user_query` both matched the *corrupted* input; they
do **not** validate intended prompt-to-report relevance. For Windows PowerShell
5.1 scripts piped into `python -`, explicitly set UTF-8 **before** piping:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
@'
text = "Проверка"
print("CYRILLIC_PIPE_PASS =", text == "\\u041f\\u0440\\u043e\\u0432\\u0435\\u0440\\u043a\\u0430")
'@ | python -X utf8 -
```

This should print `CYRILLIC_PIPE_PASS = True` **without sending a request**.
An already corrupted prompt cannot be repaired by `python -X utf8` alone.

`send()` completion does not prove research completion. No automatic retry,
report polling or browser fallback is added; an `unknown` readback must not
trigger a duplicate send. Initial support is restricted to new,
non-temporary text chats without `conversation_origin`; unsupported
combinations fail before network operations.

## Deep Research readback (experimental, read-only)

An existing *real* ChatGPT Deep Research invocation can finish its launching
assistant message before the research report is ready. Ordinary
`get_status(conversation_id).status == "completed"` is **not** proof of research
completion. The new method reads one canonical conversation snapshot, matches
the Deep Research tool invocation and its widget state, and never sends a turn:

```python
research = client.get_deep_research(conversation_id)
print(research.status)       # unknown | running | needs_input | completed
if research.status == "completed":
    print(research.report_id)
    print(research.report_text)  # verbatim product text; may contain cite markers
```

One user-run Windows readback on 2026-10-24 confirmed a completed widget
(`status=completed`), a separately finished report message, its stable ID,
and 41,762 characters of report text. This does **not** establish Direct HTTP
launch, live running-to-completed transitions, or future private-protocol stability.
The initial `venus_widget_state` may remain at plan-approval even after
completion; it is deliberately not a terminal status source. A missing,
ambiguous or malformed widget/report returns `unknown` rather than
promoting assistant-message finality. Transport/read errors still raise.

## Intended downstream integration (Codexia, HDE)

- Treat the client as a **transport**, not Work/admission/permission authority.
- Record the exact intent/Work binding before the possible external effect.
- Use server conversation/message identities and a read-only canonical history
  check when available. The requested model slug is not model-attestation.
- Do not assume a returned text stream proves canonical completion. A success
  with canonical IDs still needs the downstream application's admission policy.
- Never automatically resend after a timed-out, interrupted or otherwise
  ambiguous write. Missing history is not proof of non-submission.
- Keep credentials in `auth_data.json` outside version control. Do not print
  cookies, bearer tokens, protocol payloads or complete private documents as
  default progress output.
- Fail closed if the session expires, server challenge cannot be legitimately
  completed, or the pinned public module changes. No browser fallback.
- For downstream interactive E2E, report distinct, **sanitized** stages:
  preflight, claim/handoff committed, direct submit attempt, visible token
  stream (explicit opt-in), canonical readback, provider IDs verified,
  Work admission / yielded result. Do not report `submitted` as proven
  merely because a local function was called.

## Status of verified behavior

User-run continuous text conversations, ordinary and Temporary Chat, streaming
and more-than-one-hour session reuse have been reported on the separate PR #212
checkout. Earlier live notes also report single PNG/TXT uploads.

One Codexia delegated-Work E2E with three Markdown attachments was observed:
GPT-6 with requested `high` mapped to observed `extended`, streamed text,
verified exact assistant message readback and `CAPTURED_UNADMITTED`. This is
transport evidence, **not** Gen2 cognition admission or Work completion. It
does not prove general reliability across models, attachment formats, session
renewal or changing web-protocol revisions.

### Additional user-run Windows evidence — 2026-10-23

One request with `model="gpt-6"` and `reasoning_effort="high"` returned expected
text; the model and effort requests were not independently attested by the
server. `temporary=True` returned expected text, without a separate retention
audit. An ordinary HTTP chat accepted two Markdown documents and one PNG,
produced two observed streaming callback chunks, and retained context on a
separate-process continuation. `cwa export` returned 13 normalized messages.
A separate HTTP conversation generated a 25-byte TXT, which
`BrowserlessHTTPClient.handoff_generated_artifact(...)` materialized locally with
exact bytes, SHA-256 verification and `overwritten=False`. This is an inherited
governed ChatGPT artifact operation, not general sandbox/attachment download.

Existing-browser auth sync and canonical-GET `401` recovery are independently
proven on `ChatGPTWebClient`, but are not automatically enabled for
`BrowserlessHTTPClient.send()`. These are scoped caller-run observations,
not product-protocol or long-term stability guarantees.

This module remains **experimental and explicitly opt-in**, even when included
in `main`. Existing browser-owned ChatGPT and isolated Qwen SDK behavior remain
the default; the HTTP client has no automatic browser fallback.

No live requests are made by the `test_browserless_http_client_contract.py`
regressions; they exercise the client boundary with a mocked underlying send.
